# get-icon

[English](README.md) | 日本語

macOS と Windows で、ファイルやフォルダーのアイコンを**アルファ付きの PNG ベースのピクチャー**として返す 4D 用ネイティブプラグインです。Finder/Windows シェルのアイコン解決を使うため、OS が認識するファイル/フォルダーのカスタムアイコンにも対応します。サムネイルの生成や、カスタムアイコンのメタデータの解析をプラグイン自身が行うことはありません。

## 動作環境

- 4D 21.1 以降
- AppKit を備えた macOS、または Windows 10/11（x64）
- コマンドはコオペラティブ専用です（`threadSafe: false`）。

## コマンド

```4d
$picture:=Path Get icon($entry {; $size {; $options}})
```

マニフェストのシグネチャ：`Path Get icon(&J;&L;&L):P`

| 引数 | 型 | 意味 |
|---|---|---|
| `$entry` | Object | 存在するファイルシステム上の項目を参照する `4D.File` または `4D.Folder`。Text のパスではない |
| `$size` | Integer | 出力する正方形の一辺の物理ピクセル数。省略可能で、デフォルトは **256** |
| `$options` | Integer | オーバーレイの扱いを指定する任意の値（後述の定数を参照）。省略、**0**、または認識できない値の場合は、システムが選んだオーバーレイを使う |
| `$picture` | Picture | 成功時はエンコードされた PNG、失敗時は本当に空のピクチャー |

```4d
var $file; $folder : Object
var $picture : Picture
$file:=File("/LOGS/report.pdf")
$picture:=Path Get icon($file)
$folder:=Folder(fk database folder)
$picture:=Path Get icon($folder; 128)
// Windows の .lnk ファイルや macOS の Finder エイリアスの場合：
// $picture:=Path Get icon($shortcut; 256; Icon No shortcut arrow)
// ショートカット以外のシェルのステータスバッジも含め、対応するオーバーレイをすべて省く：
// $picture:=Path Get icon($file; 256; Icon No overlays)
If (Picture size($picture)=0)
    // パスが存在しない、サイズが無効、またはネイティブでの取得/エンコードに失敗
End if
```

4D は、宣言された Longint 引数が省略されるとゼロとして扱います。そのため、**ゼロを指定してもデフォルトの 256 ピクセルになります**。負の値は失敗します。固定している SDK には引数の有無や個数を取得する手段がなく、非公開の ABI を調べることもしていません。4 チャンネルのバッファが WIC の `UINT32_MAX` バイトを超えるサイズは、ネイティブでのメモリ確保の前に失敗します（算術的に安全な一辺の最大値は 32767 ピクセルで、両プラットフォーム共通です）。これはネイティブで表現できる範囲の上限であり、実用上のメモリを保証するものではありません。大きなサイズを要求すると、メモリ確保に失敗することもあります。SDK の符号付き 32 ビットの長さに収まる必要があるのは、エンコード後の PNG の長さだけです。

出力は画面の DPI や Retina のスケーリングに関係なく、正確に `$size` × `$size` になります。アートワークに意図的に設けられた余白も含め、元のアイコンのキャンバス全体を、切り取らずに縦横比を保って出力に収めます。ベースアイコンのビットマップが小さい場合は、ニアレストネイバー法で拡大し、ぼかさずにくっきりしたピクセルのブロックを保ちます。32×32 を 128×128 にすると 4×4 のブロックに、32×32 を 256×256 にすると 8×8 のブロックになります。縮小には高品質なフィルタリングを使います。拡大によって細部が生まれたり、アートワークに含まれる余白がなくなったりすることはありません。Windows のオーバーレイバッジは、後述のとおり別にサイズが決まります。

**Windows：** ショートカットに限らず、ファイルにもフォルダーにも、シェルが選んだオーバーレイがデフォルトで含まれます。Windows やインストールされたシェル拡張が従来のオーバーレイの仕組みで公開していれば、ショートカットの矢印、バージョン管理のステータス、同期のステータス、共有/アクセスのバッジなどが含まれることがあります。オーバーレイは Windows が 1 つ選びます。プラグインが競合するバッジを重ねたり、独自に優先順位を付けたりすることはありません。表示されるかどうかは、Windows のバージョン、インストールされているハンドラー、設定、システムのオーバーレイの空きスロットによって変わります。最近のクラウドのステータス表示は、必ずしもこの方法で公開されているわけではありません。また、別のプロセスがファイルを開いている/ロックしていることを示す汎用のバッジはありません。

Windows エクスプローラーは UAC のシールドをオーバーレイの仕組みではなく自前で描画しているため、ユーザーアカウント制御が有効な場合、プラグインは以下のファイルにシールドを別途追加します：マニフェストで `requireAdministrator`（管理者アカウントでは `highestAvailable`）を要求している実行ファイル、互換性の設定で **Run this program as an administrator** が有効な実行ファイル、**Run as administrator** が指定されているショートカット、またはそのような実行ファイルを参照しているショートカット。シールドは右下の、出力サイズの半分以内の位置に、ショートカットの矢印の下に描画されます。インストーラー名による推測は行わないため、`setup.exe` のようなファイル名だけを理由にエクスプローラーが表示しているシールドは再現されません。

`Icon No shortcut arrow`（**1**）は、システムのショートカットのオーバーレイだけを抑制します。ショートカットであっても、それとは関係のないシェルが選んだバッジや UAC のシールドは残ります。`Icon No overlays`（**2**）は、別途合成されるシェルのオーバーレイと UAC のシールドをすべて省きます。どちらのオプションでも、ベースアイコンのアートワークにもともと描かれている装飾は取り除かれません。これらは互いに排他的な指定であり、組み合わせ可能なビットフラグではありません。認識できない値の場合はデフォルトの扱いになります。

**macOS：** Finder エイリアスは、UI を表示したりボリュームをマウントしたりせずに解決されます。デフォルトでは、独自のカスタムアイコンを持たないエイリアスは、参照先のネイティブなアートワークにシステムのエイリアスバッジを重ねて合成します。これにより、フォルダーのエイリアスに対して `NSWorkspace` が返すことのある汎用の書類アイコンを避けています。エイリアス自身にカスタムアイコンがある場合は、`NSWorkspace` を通じてそのアイコンを使います。どちらの抑制オプションでも、参照先のアイコンを使います。解決できないエイリアスは明示的に失敗します。Finder Sync 拡張のバッジ、クラウドのステータス、ロックの装飾は、現在のバックエンドでは個別に対応していません。

Object の型は、4D の対応するコンストラクターでパスを変換するためだけに使われ、ディスク上の種類を制限するものではありません。ファイル、フォルダー、Finder エイリアス、Windows のショートカットは、すべて同じコマンドで扱います。`4D.Folder` でファイルやエイリアスを参照することも（例：`Folder($alias.path+"/")`）、`4D.File` で区切り文字のないネイティブパスを使ってディレクトリを参照することもできます。末尾の区切り文字はネイティブでの検索の前に取り除かれますが、ファイルシステムのルートはそのまま保たれます。Windows では、ファイル専用のアイコンメタデータや UAC のシールドの扱いを決めるのは、呼び出し側の Object の型ではなく、実際のファイルシステムの属性です。ファイルへのショートカットとフォルダーへのショートカットは同じように扱われます。リンク切れの `.lnk` でも、シェルがアイコンを提供する場合があります。ショートカットの解決のための UI、検索、リンクの追跡は一切行いません。

失敗した場合（存在しない/削除されたパス、無効な Object、メモリ確保やエンコードのエラーなど）は、透明な PNG ではなく `PA_CreatePicture(nullptr, 0)` を返します。プラグインは診断メッセージを標準エラー出力に記録します。返されたピクチャーの所有権は 4D にあります。

### 1.x からの移行

バージョン **2.0.0** では、両プラットフォームで `File Get icon` と `Folder Get icon` が **Path Get icon** に置き換わりました。4D メソッド内の古いコマンド名を両方とも置き換え、コンパイル済みプロジェクトは再コンパイルしてください。引数、デフォルトのサイズ、オーバーレイの定数、PNG の出力は変わりません。古いコマンドは非推奨の名前として残されることなく、削除されています。ファイル/フォルダーの種類が一致しない場合に拒否する動作は、意図的に廃止しました。

## 定数

**Icon options** テーマで、`constants.xlf` を通じて以下のプラグイン定数を公開しています：

| 定数 | 型 | 値 | 意味 |
|---|---|---|---|
| `Icon No shortcut arrow` | Longint | 1 | ショートカットの矢印だけを抑制し、Windows シェルのその他のオーバーレイは残す |
| `Icon No overlays` | Longint | 2 | 別途合成される Windows シェルのオーバーレイと UAC のシールドをすべて抑制し、macOS では Finder エイリアスの矢印を抑制する |

## ネイティブの実装

macOS では、`NSWorkspace.iconForFile:` と、要求されたサイズで初期化済みの 8 ビット sRGB RGBA の CoreGraphics ビットマップを使い、ニアレストネイバーでの拡大/高品質な縮小を行って、ImageIO で PNG にエンコードします。キャッシュされた `NSImage` や、現在の AppKit のグラフィックスコンテキストを変更することはありません。ネイティブでの取得、PNG のエンコード、SDK のピクチャー作成（空の結果を含む）、エラー時のピクチャーの破棄は、1 回の `PA_RunInMainProcess` コールバックで行います。引数/プロパティへのアクセスは呼び出し元の言語コンテキストで行い、完成したピクチャーは破棄されずにそこへ返されます。この境界は、リストボックスの列のデータソース式から呼び出された場合にも適用されます。SDK ではピクチャーの作成がスレッドセーフとされていますが、グラフィックスのライフサイクルが複数のコンテキストにまたがらないよう、取得と同じメインプロセスのサイクル内で行っています。

4D のメインプロセスと Cocoa のメインスレッドは、同じものとして保証されているわけではありません。ネイティブのバックエンドは、AppKit に触れる前に Cocoa のメインスレッドで実行されていることを別途確認し、そうでなければエラーを報告します。メインキューへ同期的にディスパッチすることは決してありません。これはスレッド処理の堅牢化であり、報告されている断続的なクラッシュが解決したことを証明するものではありません。

エイリアス自身のカスタムアートワークは、ネイティブの Finder カタログのフラグで検出します。`NSURLCustomIconKey` は未実装であるとドキュメントに記載されているため、非推奨のカタログ API を使っています。カスタムアートワークのないエイリアスでは、まず参照先のアイコンを描画し、その上に `/System/Library/CoreServices/CoreTypes.bundle` にインストールされているシステムの `AliasBadgeIcon.icns` を、出力キャンバス全体に高品質なフィルタリングで描画します。左下の配置と透明な余白はバッジ自身が持っているので、プラグインが Apple のアイコン素材を近似したり再配布したりすることはありません。このリソースの場所は macOS の実装に依存するものであり、公開 API の仕様ではありません。バッジが見つからない、または使えない場合は明示的に失敗します。

Windows では、実際の UTF-16 パスを `SHCreateItemFromParsingName` で解決し、`SIIGBF_ICONONLY` を指定して `IShellItemImageFactory::GetImage` を呼び出します。拡大はシェルの補間ではなく WIC に任せます。`SHGFI_ADDOVERLAYS | SHGFI_OVERLAYINDEX` を指定した `SHGetFileInfoW` で、任意の項目に対してシェルが選んだオーバーレイを取得します。オーバーレイには、要求されたサイズをカバーする最も小さいシステムイメージリストのキャンバス（small、large、extra-large、jumbo）を使い、それより大きなサイズの場合は利用できる最大のキャンバスを使います。リストの実際のサイズは、画面の DPI から推測するのではなく問い合わせて取得します。ベースアイコンと違い、オーバーレイがそのネイティブのキャンバスを超えて拡大されることはありません。jumbo のオーバーレイは、512 ピクセル以上の出力でも通常は 256 ピクセルのキャンバスのままです。透明部分を含むキャンバス全体を左下に揃えて配置し、バッジのアートワークは切り取りません。縮小にはプリマルチプライドアルファでの高品質なフィルタリングを使います。これにより、32 ピクセルのバッジが拡大されて粗く大きすぎる矢印になるのを避けています。バッジは、ベースアイコンのサイズを調整した後にアルファ合成されます。ショートカットだけを抑制する場合は、リンク上のバッジをすべて抑制するのではなく、選ばれたオーバーレイのインデックスを `SHGetIconOverlayIndexW` の標準のリンク用オーバーレイと比較します。取得とエンコードはネイティブの COM と WIC を使ってメモリ上で行い、一時ファイル、サムネイル、背景色のフラグ、GDI+ のビットマップ変換は使いません。

テストした Windows のビルドでは、`SIIGBF_SCALEUP` を指定しなくても、従来形式のアイコンをシェルで取得すると、正しく拡大されたアイコンではなく大きすぎるキャンバスが返ることがあります。そこで、シェルのネイティブなアイコンの場所のメタデータ、WIC で得た ICO のサイズ、EXE/DLL のグループアイコンリソースのサイズを使い、WIC で拡大縮小する前に元のキャンバスのサイズで取得します。実行ファイルのリソースはデータとしてのみ読み込み、実行することはありません。ショートカットのアイコンの場所や参照先も、起動せずに読み取ります。アートワークのアルファの範囲で切り取ったり、意図的な余白を取り除いたりすることはありません。この補正の対象は、ICO ファイル、ICO を元にしたシェルのアイコン、実行ファイルに埋め込まれたアイコン、およびそれらを参照するショートカットです。`.exe` という名前で ICO データを格納したアイコンファイルを持つ、Windows Installer のアドバタイズショートカットも含みます。元のキャンバスのサイズがわからない場合、シェルは小さなアイコンを要求されたキャンバスの中央に置き、薄い影の枠を付けることがあります。プラグインは、中央の領域が、より小さい標準サイズでのシェル自身の描画と完全に一致する場合に限り、それを余白とみなし、その小さいサイズの描画を拡大します。任意のサードパーティ製シェルプロバイダーは、依然として低解像度や余白付きのアートワークを返す可能性があります。

UAC のシールドは、オーバーレイと同じシステムイメージリストの選択で、`SHGetStockIconInfo(SIID_SHIELD)` から取得します。昇格が必要かどうかは、`EnableLUA` のポリシー、実行ファイルの `RT_MANIFEST` にある `requestedExecutionLevel`（リソースはデータとしてのみ読み込み）、`AppCompatFlags\Layers` の `RUNASADMIN` エントリー、ショートカットの `SLDF_RUNAS_USER` フラグまたは解決した参照先から判断します。

ファイルシステムの Object は、4D の File/Folder コンストラクターと `fk platform path` を使って再構築します。macOS のバックエンドは再構築した POSIX の `path` を受け取り、Windows は Unicode の `platformPath` をそのまま使います。SDK のプロパティの文字列は、それを所有する変数をクリアする前にコピーします。

コンストラクターに渡す文字列引数は、未定義型のSDK変数として作成してから、所有するパス文字列を設定します。固定したSDKの`PA_SetStringVariable`は既存値を破棄せずに文字列の記述子を代入するため、先に文字列型の変数を作成すると、空文字列にメモリーを確保するランタイムで初期値がリークします。代入後のパス文字列は、引数変数だけが破棄します。

## ビルドとインストール

[Releases](https://github.com/miyako/4d-plugin-get-icon/releases) から ZIP または DMG をダウンロードしてください。展開またはマウントして、**get-icon.bundle** をデータベースの **Plugins** フォルダーにコピーし、4D を再起動します。バンドルの `Contents` の階層構造は崩さないでください。どちらのダウンロードにも macOS ユニバーサルと Windows x64 のバイナリが含まれています。macOS 版は Developer ID 署名・公証済みですが、Windows 版は Authenticode 署名されていません。

このプロジェクトは、チュートリアルの `example/` にある CMake とテストプロジェクトのひな形を元にしています。サポートしているビルド方法は CMake だけです。古くなったテンプレートの IDE プロジェクトを保守するのではなく、`-G Xcode` やインストール済みの Visual Studio ジェネレーターで IDE プロジェクトを生成してください。

```sh
git clone --recurse-submodules https://github.com/miyako/4d-plugin-get-icon.git
cd 4d-plugin-get-icon
cmake -S get-icon -B get-icon/build -DCMAKE_BUILD_TYPE=Release
cmake --build get-icon/build --config Release --parallel
ctest --test-dir get-icon/build -C Release --output-on-failure
```

Windows で構成するときは `-A x64` を付けてください。macOS でユニバーサルバンドルを作るには `-DCMAKE_OSX_ARCHITECTURES="arm64;x86_64"` を追加します。CMake 3.20 以降と、macOS では Xcode、Windows では Windows SDK を含む Visual Studio が必要です。サードパーティの画像ライブラリは不要です。4D SDK はサブモジュールとしてバージョンを固定しています。

出力先は `get-icon/get-icon-test/Plugins/` です。macOS では `get-icon.bundle`、Windows では `get-icon/Contents/Windows64/get-icon.4DX` と、その隣の Resources が出力されます。そのプラグインのディレクトリをデータベースの **Plugins** フォルダーにコピーし、4D を再起動してください。ローカルでのビルドは Developer ID 署名・公証されません。

マニフェストではプロジェクト内でのみ使う ID（`31071`）を使っており、本番用に正式に割り当てられた ID であるという意味ではありません。インストールしている他のプラグインが、この ID やこれらのコマンド名を使っていないことを確認してください。

## テストと CI

`string-ownership` CTestは、実際のプラグインソースと変更していないSDK全体をエンジン境界のシムに接続し、描画せずに所有権を検証します。空文字列がnullの場合とメモリーを所有する場合の両方で、文字列、引数ハンドル、返却オブジェクトの解放を計数します。ASCII、BMP、サロゲートペアのUTF-16パスの完全一致、借用プロパティのコピー、型不一致とエラー時の後始末も確認します。これは契約レベルの回帰テストであり、すべての4Dランタイム内部の空文字列表現を認証するものではありません。

ネイティブのテストでは、ピクセルサイズ、PNG のアルファ、Unicode のパス、カスタムアイコン、従来形式のアートワーク、オーバーレイの扱い、無効な入力、繰り返しの取得を確認します。Windows の回帰テストでは、通常のファイル、フォルダー、ショートカットについて、各オーバーレイの指定をシェルが実際に選んだものと比較し、ファイルやフォルダーへのリンクについて、元のピクセルが正確に 4×4/8×8 に複製されていることと、ショートカットが左下に合成されていることを確認します。大きなバッジの回帰テストでは、従来形式の 32 ピクセルとネイティブの 256 ピクセルの両方のベースアイコンを使い、128、256、257、512、1024 ピクセルで合成したピクセルをネイティブの jumbo オーバーレイと比較して、大きな出力でバッジが拡大されないことを確認します。さらに、`.exe` という名前の Windows Installer 形式の ICO データや、`requireAdministrator` のマニフェスト、互換性レイヤーによる昇格、管理者として実行するショートカットでの UAC のシールド（右下の 4 分の 1 の範囲内に収まり、`Icon No overlays` で取り除かれること）も回帰テストの対象です。サードパーティのステータスオーバーレイは、そのプロバイダーがインストールされている必要があります。テストでハンドラーをインストールしたり、システムの関連付けを変更したりすることはありません。チュートリアルを元にした 4D のテストプロジェクトでは、統合されたコマンドについて、両方の Object の型、名前付きのオーバーレイ定数 2 つ、認識できないオプションでのデフォルトの動作、デフォルトのサイズ、デコードした PNG のサイズ、繰り返しの呼び出し、失敗時の `Picture size(...)=0` を確認します。

macOS の回帰テストでは、ファイルやフォルダーへの Finder エイリアスを末尾の区切り文字あり/なしで渡し、デフォルトの矢印と 2 つの抑制オプションを確認します。矢印付きの汎用の書類アイコンを成功とみなすのではなく、通常のフォルダー、参照先のカスタムアイコン、エイリアス自身のカスタムアイコンを含め、バッジ以外の部分のピクセルを参照先の実際のアートワークと比較します。Windows の回帰テストでは、フォルダーへのショートカットを末尾の区切り文字あり/なしで **Path Get icon** に渡し、すべてのオーバーレイの指定について `.lnk` ファイルでの結果と比較します。ファイルへのショートカット、リンク切れのショートカット、通常のファイル、ドライブのルートも対象です。4D の統合テストでは、両プラットフォームでこの経路を確認します（macOS では拡張子のないエイリアス、Windows では `.lnk` のショートカット）。

統合テストは、対応するバージョンの [tool4d](https://developer.4d.com/docs/Admin/cli/) ランタイム（ライセンス不要）で実行します：

```sh
/path/to/tool4d --dataless --startup-method=test_all \
  --project="$PWD/get-icon/get-icon-test/Project/get-icon.4DProject"
```

正常終了したことと、`PASS` という出力行が正確に出たことの両方を確認してください。tool4d はランゲージエラーが起きても終了コード 0 で終わることがあるためです。統合テストではさらに、別のコオペラティブな 4D プロセスで、256 ピクセルと 31 ピクセルのプラグインのアイコン取得とネイティブの `.getIcon()` 呼び出しを交互に 100 回繰り返します。macOS の SDK コールバック用のテストハーネスでは、ディスパッチの失敗も含めて、描画、ピクチャーの作成、失敗時の後始末がメインプロセスのコールバック内に収まっていることと、ピクチャーを返すと呼び出し元のコンテキストに所有権が移ることを確認します。これらのチェックは、対話的なリストボックスのデータソースの評価を再現するものではありません。`.github/workflows/test.yml` は、push、プルリクエスト、手動実行のたびに、macOS と Windows でビルドし、ネイティブ/4D のテストを実行します。

**通常のビルドと PR のテストに独自のシークレットは不要です。** チェックアウトには、GitHub が自動で発行する、コンテンツへの読み取り専用アクセス権を持つ `GITHUB_TOKEN` を使います。tool4d は公開されているものをダウンロードし、ライセンスのアクティベーションは不要です。CI はさらに、テスト済みのネイティブバイナリをステージングし、ソースと結び付いたマニフェストを確認し、同じ実行内での macOS/Windows のアーティファクトの受け渡しを実際に検証します。テスト専用のアドホック署名で、厳密なバンドル検証、ZIP/DMG の往復、統合したプラグインのスモークテストを行いますが、これが配布物としてアップロードされたり、本番の署名で受け入れられたりすることはありません。短期間だけ保持されるビルドの入力は、署名済みの配布パッケージではありません。

## 署名済みの配布パッケージ

`.github/workflows/release.yml` は、**macOS の Developer ID Application による署名と Apple の公証**を行います。Windows の Authenticode 署名は意図的に実装していないため、同梱の Windows 用 `.4DX` は未署名のままです。

新しいリリースの前には毎回、GitHub Actions で **main** から **Bump version**（`.github/workflows/bump-version.yml`）を手動で実行し、**patch**（デフォルト）、**minor**、**major** のいずれかを選びます。このワークフローは `VERSION` を検証し、対象のバージョンにすでにタグがある場合は拒否し、自動で発行される `GITHUB_TOKEN` を使って新しいバージョンを **main** に直接コミットします。独自のシークレットは不要です。リポジトリのルールで、このワークフローによる main への push を許可しておく必要があります。タグの作成やリリースの開始は行いません。代わりに、プルリクエストで `VERSION` を未使用のセマンティックバージョンに更新し、**main** にマージしてもかまいません。

次に、GitHub Actions で **Build and Release** を手動で実行し、**main** を選びます。失敗したワークフローを再実行すると元のコミットが使われ、その後のバージョンのバンプは反映されません。新たに実行し直してください。それ以外の ref は、本番のジョブと署名スクリプトで拒否されます。実行時の不変のコミットが、両プラットフォーム、既存のネイティブ/tool4d のテスト、入力のマニフェスト、パッケージングのすべてに使われます。バージョンの唯一の情報源は `VERSION` のままであり、リリースのワークフローがバージョンを上げたりコードをマージしたりすることはありません。

署名、公証、検証、パッケージのスモークテストがすべて成功した後に限り、別の公開用ジョブが `contents: write` を受け取ります。このジョブは実行時のコミットに正確に `v<VERSION>` を作成し、GitHub Release を下書きとしてアップロードし、アップロードしたアセットをダウンロードしてチェックサムを検証したうえで公開します。既存のタグが移動されることはありません。別のコミットを指すタグや既存のリリースがある場合は、アセットを上書きせずに公開を中止します。下書きのアップロードに失敗した場合は、公開リリースにはならず、確認用の下書きとして残ります。それ以外のジョブと通常の CI はすべて読み取り専用のままです。

ワークフローは macOS ユニバーサルバイナリと Windows x64 バイナリをビルドし、それぞれのハッシュ、バージョン、ソース/SDK のコミットを検証して、ポータブルなプラグインを 1 つ組み立てます：

```text
get-icon.bundle/
  Contents/
    Info.plist
    MacOS/get-icon
    Windows64/get-icon.4DX
    Resources/manifest.json
    Resources/constants.xlf
```

パッケージングと検証のユーティリティは Python 3.11 以降とその標準ライブラリを使います。ホスト型ランナーにはこれが用意されており、追加の Python パッケージは不要です。

バンドルには、Hardened Runtime とセキュアタイムスタンプ付きで Developer ID 署名が施されます。署名に使う ID と生成された署名は `NOTARYTOOL_TEAM_ID` と一致している必要があります。検証の失敗、認証情報の欠落、署名のエラー、または **Accepted** 以外の公証ステータスでは、ワークフローが失敗します。本番でアドホック署名や未署名にフォールバックすることはありません。DMG のコンテナは別途署名・公証され、その後ステープルが付けられ、検証され、Gatekeeper による評価を受けます。ZIP も公証されますが、ZIP 自体にはステープルのチケットを付けられません。ステープル付きのダウンロードが必要な場合は DMG を使ってください。

両方の形式が合格すると、ZIP を展開して最終的なファイル構成と署名を検証し、アーティファクトをアップロードする前に、実際にパッケージされたプラグインを tool4d で実行します。成功した実行から `get-icon-signed-packages-<commit>` をダウンロードしてください。ZIP、DMG、公証レポート、`PROVENANCE.json`、`SHA256SUMS` が含まれています。パッケージにはプラグイン/SDK のライセンスと、署名前のネイティブのハッシュであることを明記した `BUILD-PROVENANCE.json` が含まれます。`PROVENANCE.json` は署名済みのペイロードの一覧であり、`SHA256SUMS` は**署名と DMG へのステープル付けの後の**最終的なアーカイブのハッシュです：

```sh
shasum -a 256 -c SHA256SUMS
xcrun stapler validate get-icon-1.0.0.dmg
spctl --assess --type open --context context:primary-signature get-icon-1.0.0.dmg
```

### 必要な署名用シークレット

提供されている移行用プラグインのワークフローと同じ 6 つの名前を使います。**Settings > Secrets and variables > Actions** でリポジトリシークレットとして設定するか、**release-signing** 環境のシークレットとして設定してください：

| シークレット | 用途と設定方法 |
|---|---|
| `APPLE_DEVELOPER_ID_CERTIFICATE` | macOS のキーチェーンアクセスから、**Developer ID Application** 証明書を秘密鍵とともに `.p12` として書き出し、`base64 -i certificate.p12 \| pbcopy` でエンコードして、その値を貼り付ける。Apple Development 証明書では不十分。 |
| `APPLE_DEVELOPER_ID_CERTIFICATE_PASSWORD` | その `.p12` を書き出すときに設定したパスワード。 |
| `KEYCHAIN_PASSWORD` | CI の一時キーチェーン専用に用意した、新しい強力なランダムパスワード。 |
| `NOTARYTOOL_APPLE_ID` | Apple Developer のチームで権限を持つ Apple ID のメールアドレス。 |
| `NOTARYTOOL_TEAM_ID` | チームの 10 文字の ID。Apple Developer アカウントのメンバーシップの詳細で確認できる。署名証明書のチームと一致している必要がある。 |
| `NOTARYTOOL_PASSWORD` | [account.apple.com](https://account.apple.com/) の **Sign-In and Security > App-Specific Passwords** で作成した App 用パスワード。 |

PAT、GitHub App の認証情報、Windows の証明書、追加の 4D ライセンスは不要です。ワークフローは一時的なキーチェーンを使い、署名ツールだけにアクセスを許可し、終了時に削除します。承認を必須にしたい場合は、**Settings > Environments > release-signing** で main のみにデプロイを制限し、必須のレビュアーを設定してください。これによって通常の PR のジョブにシークレットを置く必要が生じることはありません。

本番の Developer ID 署名、公証、Gatekeeper による受け入れは、これらの認証情報を設定した後に、権限のある実行で検証する必要があります。シークレットを使わない CI で検証するのは、ネイティブのビルド、アーティファクトの受け渡し、パッケージの構成/来歴、署名チェックが失敗時に安全側に倒れることであり、実際に署名・公証された配布物が作成されたことを示すものではありません。
